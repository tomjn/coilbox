# Real-star galaxy for galactic conquest

A conquest map built from the actual solar neighbourhood instead of a procedural scatter. Sol sits at the centre and is the player's homeworld. Every star within the chosen radius appears, at its real position in three dimensions, rendered as its real spectral class. Only the seed-driven details vary: factions, maps, difficulty, and enemy starting locations.

## Why

The procedural galaxy is varied but weightless. A map where Barnard's Star really is 6 light years out, and Sirius really is a blue-white A-class star with a white dwarf companion, gives the campaign a spine the generator cannot invent.

## Scope

In: a committed star catalogue, a build script that produces it, a third position component in the galaxy schema, a real-star source in the generator, a jump-range lane rule, spectral-class rendering, and a wizard entry.

Out: anything beyond 19 light years, planets, star motion over time, and any change to how battles are fought.

## Decisions taken

- The catalogue is generated by a script and committed. Runtime never fetches.
- Merging of binary and multiple systems happens in the script, so the committed file is system-level.
- Sol is always the player capital.
- Star visuals reuse the existing seven `STAR_TYPES`, plus one new brown dwarf entry.
- Lanes link systems within a fixed jump range rather than by nearest neighbours.
- The wizard exposes this as a new entry in the existing Shape dropdown.
- Source is RECONS, whose measurements carry no share-alike obligation, keeping the repo wholly MIT.

## Data

### Source

The [RECONS nearest 100 star systems](http://www.recons.org/TOP100.posted.htm) table, accurate as of 1 January 2012, reaching 21.4 light years. It gives name, RA, declination, trigonometric parallax and spectral type per component, which is everything needed.

Their server presents a certificate for `astro.gsu.edu`, so it does not serve `recons.org` over TLS cleanly. A raw snapshot is checked in under `scripts/data/recons-top100.html` and the build reads that. This makes the build reproducible and makes any data change reviewable as a diff.

### Supplement

The RECONS table predates two nearby discoveries that fall well inside our radius:

- Luhman 16 (WISE J104915.57-531906.1), a brown dwarf binary at 6.5 ly, discovered 2013
- WISE 0855-0714, a brown dwarf at 7.3 ly, discovered 2014

These live in `scripts/data/supplement.json`, each row carrying its own citation. The supplement is merged during the build.

Stated honestly in the catalogue header and in the docs: the supplement covers the two well-known post-2012 additions inside the radius, but the census of very faint brown dwarfs is not closed. This is a dated snapshot rather than a guarantee of completeness.

### Build script

`scripts/build-star-catalogue.mjs`, wired as `bun run stars:catalogue`, matching the existing `.mjs` script convention.

It parses the RECONS table, merges the supplement, groups components into systems, converts to Cartesian coordinates and writes `src/conquest/realstars/catalogue.json`.

Coordinates use the standard equatorial convention with Sol at the origin, `+X` toward the vernal equinox and `+Z` toward the north celestial pole:

```
d = 3.2615638 / parallax_arcsec     # light years
x = d * cos(dec) * cos(ra)
y = d * cos(dec) * sin(ra)
z = d * sin(dec)
```

This matches the convention HYG uses, so a future cross-check needs no transform.

Grouping: rows carrying a rank number start a system, and unranked rows that follow are its components. A system takes the primary's position, the common name where the table gives one, and one spectral entry per component. Alpha Centauri A, B and Proxima collapse to a single node named Alpha Centauri with three components.

Before writing, the script asserts known values and fails loudly otherwise:

- Proxima Centauri at 4.24 ly, within 0.05
- Sirius at 8.60 ly, within 0.05
- Sol at the origin
- 15 individual objects within 10 ly, resolving to 10 systems

A silent parse drift that produces a plausible but wrong galaxy is the main risk in this feature. These assertions are what catch it.

### Output shape

```ts
interface CatalogueSystem {
  name: string;              // "Alpha Centauri"
  distance: number;          // light years from Sol
  pos: [number, number, number];
  components: string[];      // ["G2.0 V", "K0 V", "M5.5 V"], brightest first
}
interface Catalogue {
  source: string;
  epoch: string;
  generatedBy: string;
  systems: CatalogueSystem[];   // ascending distance, Sol first
}
```

## Schema

Two optional, backward-compatible additions to `src/conquest/model.ts`.

`GalaxyNode.pos` becomes `[number, number] | [number, number, number]`. `parseGalaxyJson` already validates `pos.length >= 2` and reads indices 0 and 1, so it gains a third read defaulting to `0`. Every existing galaxy on disk keeps parsing unchanged.

`GalaxyNode.star?: { spectral: string[] }`, one spectral type per component, brightest first. Absent on procedural nodes, whose appearance stays hash-driven exactly as today. A hash of the node id cannot know Sirius is an A1 V with a white dwarf companion, so this is the channel that carries it.

`GalaxyDoc.generated` gains `layout: "realstars"` and `radiusLy?: number`, so a real-star galaxy rerolls in place like any other.

Nothing else moves. Links, owners, difficulty, battle specs and run state are unaffected, so saved runs reconcile normally.

## Generator

The existing generator already separates placing points from making a galaxy out of them. `scatterFor` returns bare coordinates and everything after is agnostic. This widens that seam rather than inventing one.

```ts
interface SourceStar {
  pos: [number, number, number];
  name?: string;        // absent, so starName() fills it
  spectral?: string[];
  home?: boolean;       // Sol, which becomes the player capital
}
type Linker = "knn" | "range";
```

The four procedural scatters become sources emitting `z: 0` and no name, so their output is identical to today. The real-star source reads the catalogue and filters by radius.

Six behaviours differ between the modes, and all of them are carried by the source rather than by branches:

| Behaviour | Procedural | Real stars |
|---|---|---|
| Positions | 2D scatter, `z: 0` | catalogue, real 3D |
| Names | `starName()` from naming pools | real names from the catalogue |
| Star class | hash of node id | `spectral` on the node |
| Lanes | k-nearest with crossing prune | jump range |
| Player capital | westernmost node | the `home` star, Sol |
| Node count | the size knob, clamped 8 to 80 | falls out of the radius, clamped 5 to 80 |

The node-count floor drops to 5 for real stars because an 8 light year radius yields only 6 systems.

Naming pools and `limitToNamed` do not apply in real-star mode. A game's lore star names are deliberately ignored, because the point of the mode is the real names. Faction names, colours and sides still come from the game's lore exactly as before.

### Lanes

`buildLinks` gains a 3D distance function. The crossing-prune step is dropped for the range linker, because two segments properly crossing in 3D is vanishingly rare, and testing it in projection would prune lanes that do not actually cross.

The range linker connects any two systems within 8 light years, then reuses the existing union-find repair to bridge stranded systems to their nearest neighbour.

The range was measured rather than guessed. The real neighbourhood is sparser than it looks: at 6 light years a 12 light year galaxy fragments into 7 disconnected pieces, so the repair would end up inventing most of the map. At 8 light years the graph holds together with 1.7 to 2.2 lanes per system across every offered radius, which matches the density the procedural maps already have. Crowded regions end up densely connected while isolated stars hang off one or two lanes, which no uniform nearest-neighbour rule would produce.

Procedural sources keep the k-nearest linker unchanged, so existing galaxies do not shift.

## Rendering

`layoutNodes` uses `pos[2]` when present, scaled by the same factor as X and Z so the vertical spread stays true to the horizontal one. It keeps the existing hash jitter only when the third component is absent.

`starTypeFor` takes an optional spectral string and maps its leading class to the existing types, falling back to the hash when absent:

| Spectral | Type |
|---|---|
| O, B | blue giant |
| A | white star |
| F | white star |
| G | yellow star |
| K | orange dwarf |
| M | red dwarf |
| L, T, Y | brown dwarf (new) |
| D | white dwarf |

Luminosity class III or brighter promotes M and K to red giant, and O, B and A to blue giant. No star within 19 ly is a giant, so this path is for correctness rather than for anything currently on the map.

The new brown dwarf entry is small and dim, deep red, with minimal glow.

`starSystemFor` takes the companion from `spectral[1]` when present rather than rolling the 1-in-6 binary hash, so Sirius always has its white dwarf.

The exotic roll, meaning pulsars, gas giants and dyson swarms, is suppressed on nodes carrying real spectral data. There is no pulsar within 19 light years and inventing one would undercut the whole mode.

`nodeBodyLabel` reports the real class.

## Wizard

`LAYOUT_OPTIONS` gains "Real stars, the solar neighbourhood". The existing "Random" shape deliberately excludes it, so a reroll never lands on it unasked.

Selecting it swaps the Galaxy size row for a radius picker, each option showing the resulting count:

| Radius | Systems |
|---|---|
| 8 ly | 6 |
| 10 ly | 10 |
| 12 ly | 23 |
| 14 ly | 33 |
| 16 ly | 48 |
| 19 ly | 70 |

Counts are computed from the built catalogue rather than hardcoded, so they cannot drift from the data.

Opposition, starting systems, fog of war and seed all keep working unchanged.

## Testing

- Catalogue integrity: Sol at the origin, Alpha Centauri carries three components, distances ascend, each radius yields its expected count.
- Build script: the assertions above, exercised against the committed snapshot.
- Generator: a real-star galaxy makes Sol the player capital, uses real names, produces non-zero Z, links only within range, and stays connected.
- Layout: `pos[2]` is honoured when present, and the hash jitter applies when it is not.
- Star types: the spectral mapping table, including white dwarfs and brown dwarfs.
- Regression: procedural galaxies generated before and after this change are identical.

## Risks

The dominant risk is wrong data presented confidently. It is mitigated by build-time assertions on known values, per-row citations in the supplement, and a stated epoch in the catalogue header.

The secondary risk is the lane rule producing a poorly connected map at small radii, where six systems spread over 8 light years may need heavy bridging. The connectivity repair handles it, but the resulting map may be close to a chain.
